# ADR-003: Correct use of Class Table Inheritance pattern when nesting situation

**Status:** Proposed  
**Date:** 2025-07-07

## 💭 Context

When implementing database, and considering that we are using class inheritance pattern for "is-a" relationship problem. For example: a `WebVulnerability` is a type of `Vulnerability`, and a `NetworkVulnerability` is also a type of `Vulnerability`. They share common traits such as a title, a description, and a severity, but each has unique fields. For instance, a web vulnerability has a `wasc_id`, while a network vulnerability needs a `cve_id`.
Additionally, there is a another table of `WebVulnerabilityInstances` that is direct specialization of `WebVulnerability`.
One can model, that `WebVulnerabilityInstances` is related to `Vulnerability` for a better query of data, how is when having this nesting situation of inheritance?


## 💡 Decision
When having nested inheritance is better to be related to the first parent, otherwise, there can be that other child that has a parent in common have data that does not correspond to its domain. For instance having that `WebVulnerabilityInstances` is related to `Vulnerability` will cause that `NetworkVulnerability` can have `WebVulnerabilityInstances` where does not belong to the domain.

## 💡 Justification

The core principle of Class Table Inheritance is to maintain a clear and strict parent-child relationship in the database schema, mirroring the domain model's inheritance hierarchy. When dealing with nested inheritance (i.e., specializations of specializations), it is crucial that each child table references its **direct parent** rather than a more generic ancestor.

If a deeply specialized table (e.g., `WebVulnerabilityInstances`) is linked directly to the base table (`Vulnerability`), this opens the possibility for invalid associations—such as instances being linked to unrelated vulnerability types (e.g., `NetworkVulnerability`). This breaks domain integrity and can lead to data anomalies, incorrect query results, and increased complexity in application logic to enforce correct relationships.

By always relating a specialized table to its immediate parent (e.g., `WebVulnerabilityInstances` → `WebVulnerability` → `Vulnerability`), we ensure:

- **Domain Integrity:** Only valid associations are possible, preventing unrelated types from being linked.
- **Clear Hierarchy:** The database schema accurately reflects the domain model's inheritance structure.
- **Simpler Logic:** Application code and queries can rely on the schema to enforce correct relationships, reducing the need for additional checks.
- **Maintainability:** The schema remains understandable and extensible as new specializations are added.

This approach avoids the anti-pattern of "short-circuiting" the inheritance chain and ensures that each table's data is always relevant to its specific context within the domain.
