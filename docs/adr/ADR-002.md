# ADR-002: Modeling "Is-A" Relationships in SQL

**Status:** Proposed  
**Date:** 2025-07-03

## 💭 Context

When designing a database, you'll often face a common challenge:  
How do you store items that are similar, but not identical?  
This is the classic "is-a" problem. For example: a `WebVulnerability` is a type of `Vulnerability`, and a `NetworkVulnerability` is also a type of `Vulnerability`. They share common traits such as a title, a description, and a severity, but each has unique fields. For instance, a web vulnerability has a `wasc_id`, while a network vulnerability needs a `cve_id`.

So, what's the cleanest way to model this in a relational database?

## 💡 Decision
After evaluating our requirements and the trade-offs of each approach, **we have decided to use the Class Table Inheritance pattern** for modeling "is-a" relationships in our SQL schema.

This decision is driven by the need for strong data integrity, schema normalization, and clear separation of subtype-specific fields. In our context, vulnerabilities share common attributes (such as title, description, and severity), but each subtype (e.g., `WebVulnerability`, `NetworkVulnerability`) introduces unique fields that should be enforced at the database level. For example, a web vulnerability must have a `wasc_id` and a URI, while a network vulnerability must have a `cve_id`.

## 💡 Justification

We explored two primary patterns and one anti-pattern for modeling "is-a" relationships in SQL:

### Pattern 1: Single Table Inheritance (The One Big Table)

- All fields for all subtypes are stored in a single table.
- A "discriminator" column (e.g., `vuln_type`) identifies the subtype.
- Fields not relevant to a subtype are set to `NULL`.

**Schema Example:**
```sql
CREATE TYPE vulnerability_type_enum AS ENUM ('NETWORK_OS', 'WEB');

CREATE TABLE "vulnerabilities" (
  "id" uuid PRIMARY KEY,
  "title" varchar(512) NOT NULL,
  "severity" varchar(50) NOT NULL,
  "vuln_type" vulnerability_type_enum NOT NULL, -- The discriminator
  -- Network/OS Specific Fields
  "cve_id" varchar(255), -- NULL for Web Vulnerabilities
  -- Web Specific Fields
  "uri" text,            -- NULL for Network/OS Vulnerabilities
  "param" text           -- NULL for Network/OS Vulnerabilities
);
```

**Pros:**

- ✅ **Simple Queries:** Retrieving all data for an item is straightforward—no JOINs are required, which simplifies application code.
- ✅ **High Performance:** Reading from a single table is generally faster than performing joins across multiple tables.

**Cons:**

- 🚫 **Wasted Space & NULLs:** The table can become very "wide" and filled with NULL values for fields that don't apply to every subtype.
- 🚫 **Weaker Data Integrity:** You can't enforce a NOT NULL constraint on subtype-specific fields (like `uri` or `cve_id`) because they must be NULL for other types. This shifts responsibility for data integrity from the database to the application.

### Pattern 2: Class Table Inheritance (Base + Specialization)
- A base table holds common fields.
- Specialized tables hold subtype-specific fields, linked one-to-one to the base.

**Schema Example:**
```sql
CREATE TABLE "vulnerabilities" (
  "id" uuid PRIMARY KEY,
  "title" varchar(512) NOT NULL,
  "severity" varchar(50) NOT NULL,
  "vuln_type" vulnerability_type_enum NOT NULL
);

CREATE TABLE "network_os_vulnerabilities" (
  "vulnerability_id" uuid PRIMARY KEY REFERENCES "vulnerabilities"("id"),
  "cve_id" varchar(255) NOT NULL
);

CREATE TABLE "web_vulnerabilities" (
  "vulnerability_id" uuid PRIMARY KEY REFERENCES "vulnerabilities"("id"),
  "uri" text NOT NULL,
  "param" text
);
```
**Pros:**

- ✅ Excellent data integrity (can enforce NOT NULL on subtype fields).
- ✅ Schema purity and normalization.

**Cons:**

- 🚫 More complex queries (JOINs required).
- 🚫 More overhead for inserts (multiple tables).

### Anti-Pattern: Concrete Table Inheritance
- Each subtype has its own table, duplicating all common fields.
- Querying all vulnerabilities requires UNIONs.

**Cons:**

- 🚫 Massive data duplication.
- 🚫 Difficult queries and maintenance.

### Comparison of Inheritance Patterns

| Feature               | Single Table Inheritance | Class Table Inheritance |
|-----------------------|:-----------------------:|:----------------------:|
| **Query Simplicity**  | ⭐ Excellent            | Fair                   |
| **Data Integrity**    | Fair                   | ⭐ Excellent            |
| **Performance (Reads)** | ⭐ Excellent          | Good                   |
| **Schema Purity**     | Good                   | ⭐ Excellent            |

For most modern applications, Single Table Inheritance is the most pragmatic and popular choice due to its simplicity and performance.
If absolute data integrity is required and query complexity is acceptable, Class Table Inheritance is a robust solution.
Finally, we must avoid Concrete Table Inheritance due to its drawbacks.
